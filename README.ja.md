# gama 🐸 — ローカル LLM を組み合わせる

[![CI](https://github.com/akihidem/gama/actions/workflows/ci.yml/badge.svg)](https://github.com/akihidem/gama/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)
[![Python 3.10+](https://img.shields.io/badge/python-3.10%2B-blue.svg)](https://www.python.org/)
[![deps: stdlib only](https://img.shields.io/badge/deps-stdlib%20only-brightgreen.svg)](pyproject.toml)

**各タスクを得意な小型ローカルモデルへ振り分け、複数を束ね（mixture of agents）、道具を
持たせ、どの組み合わせが大きいモデルに並ぶかをベンチで測る。stdlib only。全部ローカル。**

> **きっかけの発見**: 難問スイートで、小型ローカルモデルの*構造化された組み合わせ*（7B +
> 24B + 32B ＋ 電卓ツールをタスク別に振り分け）が **単体の 122B と同点（0.92 vs 0.92）** ──
> 1 台の Mac だけ・クラウドなし。コピーを重ねても（無意味）、素朴に束ねても（0.83）ダメで、
> **各タスククラスを正しい軽量機構へ振る**ことで並んだ。規模でなく構造。

`gama` は、その組み合わせを*あなたの*ハードで作って測るツール。そして「**どの小型モデル＋
道具＋振り分けが大きいモデルに並ぶか**（どのハードで）」を持ち寄って育てる場。

## なぜ
暗算できない小型モデルも `print(...)` を書いて実行すれば解ける。ある種の推論が弱いモデルも
アンサンブルで多数決にかければ救える。コード特化モデルは汎用モデルにコードで勝つ。**タスク別
に正しい小型の専門家を組み合わせれば、大きいモデルに並べる** ── ローカル・主権的・安価に。

## インストール
```bash
pip install git+https://github.com/akihidem/gama        # または: pip install gama-llm
# 開発するなら:
git clone https://github.com/akihidem/gama && cd gama && pip install -e .
```
依存ゼロ ── 純 Python ≥ 3.10。

## 30 秒クイックスタート
gama は OpenAI 互換のローカルサーバ（**ollama**・**MLX `mlx_lm.server`**・**LM Studio**・
**vLLM**）と subprocess CLI を叩く。
```bash
# 無料・決定的スモーク（モデル不要）:
gama bench --backends echo

# 自分のローカルモデルをクラス別に測り、振り分け表を提案:
gama bench --backends ollama --tier large --propose routing.json
```

## 部品
| backend | 役割 |
|---|---|
| `ollama`, `ssh-openai` | ローカルモデルを呼ぶ（HTTP、または SSH 越しの OpenAI サーバ＝ポート非開放） |
| **`GamaBackend`** | タスククラスで **振り分け** 1→1（実測の `routing_table`） |
| **`EnsembleBackend`** | 同一タスクに N モデルを **合議**（`synthesize` / `majority` / `first`） |
| **`ToolBackend`** | **道具(PAL)**：モデルに Python を書かせて実行（正確な計算など） |
| **`MeshflowBackend`** | **段階委譲**：外部検証で gate した安→強エスカレーション＋縁で合議＋高stakesは人間膜（AIネイティブの*組織の形*） |
| **`ABMCTSBackend`** | **探索**：ノード毎に**幅を広げる**（新規候補）か**深く掘る**（既存を改良）かを Thompson サンプリングで決める。報酬＝外部検証。幅を広げる時にどのモデルを呼ぶかも bandit（Multi-LLM AB-MCTS） |

JSON で自由に合成（`build_backend`）：`tool` / `ensemble` / コーダーの上に `gama` ルータを
乗せた*主権的スタック*を、単体の大きいモデルとベンチで比べられる。
```bash
gama bench --backends gama,ssh-openai --config recipes/mac-studio-mlx/config.json --tier large
```

### meshflow ── *組織*としての構造
振り分け・合議はモデルを*静的に*束ねる。`MeshflowBackend` は欠けていた「形」＝**検証エスカレーション**
を足す。まず一番安いティアを試し、**外部の `verify(artifact)→score` が通ったときだけ**採用（モデルの
自己申告でなく）。通らなければ強いティアへ昇格。どの単独ティアも通らない**縁**では試行を**合議**（誤りが
相補的だから効く）。なお未解決で stakes が高ければ黙って ship せず `<<NEEDS_HUMAN>>` を返す＝薄い人間
統治膜。こうして**普段は安いティアで済ませ、検証が要求したときだけ強いティアに届く**。
```bash
gama run "<task>" --config examples/meshflow.example.json --task-type code_implementation
gama bench --backends meshflow,ssh-openai --config examples/meshflow.example.json --tier large
```
これは「規模でなく構造」を*組織*の実行系にしたもの ──
[`soshiki-genron`](https://github.com/akihidem/soshiki-genron)（組織原論）研究repo
（`experiments/meshflow.py`・PAPER §6.5「採用すべき組織図」）で第一原理から導かれ、frontier モデルに
低コストで並ぶことが示された形を、gama に移植した。

### AB-MCTS ── *適応探索*としての構造
振り分け・合議・meshflow は組み合わせの「形」を**事前に**決める。`ABMCTSBackend` はその形を推論時に
適応させる。探索木を育てながら、**どのノードでも**次の 1 コールを**幅を広げる**（まったく新しい候補を
生成）か**深く掘る**（既存の候補を改良）かを Thompson サンプリングで選ぶ ── 報酬は外部の
`verify`→score。各 worker が 1 つの bandit *アクション*なので、幅を広げる手番では*どの*モデルを呼ぶかも
オンライン学習される＝小型モデルの束がそのまま **Multi-LLM AB-MCTS** になる。実装は Sakana AI
*"Wider or Deeper? Scaling LLM Inference-Time Compute with Adaptive Branching Tree Search"*
([arXiv:2503.04412](https://arxiv.org/abs/2503.04412)・NeurIPS 2025、blog
[sakana.ai/ab-mcts](https://sakana.ai/ab-mcts/)、OSS [SakanaAI/treequest](https://github.com/SakanaAI/treequest)）
の閉形式版 **AB-MCTS-A** を stdlib のみで移植したもの。`verify` スコアが既に `[0,1]` なので Beta 共役の
Thompson サンプリングは `random.betavariate` だけで済み、numpy/scipy/PyMC は要らない:
```bash
gama run "<task>" --config examples/abmcts.example.json --task-type code_implementation
gama bench --backends abmcts,ensemble,ssh-openai --config recipes/mac-studio-abmcts/config.json --tier large
```
「深く掘る」は親の回答**とそのスコア**を改良プロンプトに戻す ── これが深さを幅（＝ただの best-of-N）に
潰さない唯一の勘所。正直な検証は「探索が単体モデルに勝つか」ではなく「*適応的な*幅/深さ探索が、同じ
モデル群の*幅だけ*の best-of-N に勝つか」なので、対照として `ensemble` を並べて回し
（`recipes/mac-studio-abmcts` 参照）、`last_trace` で勝ったノードが本当に depth > 1 で `refine` されて
いるか確認すること。移植の線引きは `trinity.py` と同じ正直さで、実装したのは AB-MCTS-A であり、MCMC
ベースの AB-MCTS-M（PyMC が必要で stdlib-only を壊す）ではない。

### 構造が*割に合うか*を測る ── `bench --suite hard` / `market` / `mesh`
合議や段階委譲が効くのは特定の条件下だけ。gama は推測でなく**自分のモデルで測れる**ようにする。
既定の bench suite は天井効果（良いモデルは全部 1.0 で判別不能）なので、まず判別 suite に切り替える:
```bash
gama bench --backends ollama,ssh-openai --suite hard        # or: --suite brutal, --suite wide
```
`hard` / `brutal` は*難しく*する suite で、**`wide`** は*広く*する suite（40 問・5 クラス各 8 問・
難易度は `hard` と同じ帯）。深さは 2 つの backend を順位づけるのに要り、広さは suite を
search / confirm / sealed に**割る**のに要る（後述の `gama grow`。26 問しか無いと confirm が
5 問になり、1 問が得点の 0.2 を動かしてしまう）。全 suite の正解は
`tests/test_suite_integrity.py` が参照解から再導出している。答えが間違っている case は、
正解したモデルを黙って減点するため。

`wide` の実測（2026-08-18・WSL2・CPU のみの ollama。箱が違えば変わるし、CI は
この数字を守っていない）: `llama3.2:3b` **0.550** / `qwen2.5:7b` **0.725** /
`qwen2.5-coder:7b` **0.817**。能力の順に並び、天井にも当たっていない。割って使う前に suite が
満たすべき条件はここ。40 問のうち 19 問がこの 3 つを判別し、17 問は 3 つとも解ける
（無駄ではなく、易しいクラスを*壊す*変異を捕まえる役に立つ）、4 問はどれも解けない。

**`--suite steep` は、他の suite を既に飽和させたモデル向け。** `gemma4:e2b` は他5 suite を
まとめたプールで 0.95 を取り、封印 20 問に対する伸びしろが 1 問しか残らない。そこでは
`gama grow` は何も昇格させられず、止めているのはループではなく天井の方になる。`steep` は
厳密な冪剰余・階乗の末尾ゼロ・CSV のエスケープ・LRU の退避順など 20 問で、**7B が頭で解くには
難しく、プログラムなら大半が自明**。構造が効く余地を残してある。実測: `llama3.2:3b` **0.468** /
`qwen2.5:7b` **0.683** / `gemma4:e2b` **0.894**。正直な限界として、gemma4 は 20 問中 16 問を
完答しており、これは天井を上げただけで取り払ってはいない。

**`--suite graded` だけは分数で採点する。** 他の suite は実質 pass/fail なので、スコアは
case 単位でしか動かない。graded の 20 問は 1 問が独立に検証できる要件を複数持ち（小問 3 つ、
書式制約 4 つ、CSV セル 6 つなど）、満たした割合を返す。決定的なまま、判定モデルも無しで、
粒だけ細かくする。これが要る理由は 2 つ: `gama grow` の「confirm 1 問ぶん」の床が固定定数と
違う結果を出すのは、実際の改善が**半問と 1 問の間**に落ちた時だけで、pass/fail ではそこに
落ちようがない。もう 1 つは `abmcts` のような推論時探索が verify スコアを reward にして
進むため、二値だと「深く掘る」枝が磨く先を持たない。同じ箱での実測で、測定の
**35% / 22% / 15%**（3B / 7B / 7B-coder）が 0 と 1 の厳密な間に落ちた（観測値 0.33, 0.43,
0.5, 0.6, 0.67, 0.75, 0.8。1/2 刻みではなく 1/5・1/7 も出る）。正直な注記として、graded は
`wide` より**易しい**（平均 0.73 / 0.90 / 0.94）ので、勾配を得る用途に使い、強い backend の
判別には使わない。
**`gama market` ── いつ「束ねる」が「大きくする」より安いか？** 検証エスカレーション（meshflow）が
単体最強を Pareto 支配するのは、**安いティアの完全解率 `p` がコスト比 `w/s` を超えるとき**（`p > w/s`）。
`gama market` はあなたのティア（安→高）で bench を回し、コスト・正答率・支配の verdict を出す:
```bash
gama market --backends gemma,haiku --suite hard --costs 1,10
```
**`gama mesh` ── 「合議」は本当に効くか？** メンバの答えを 1 つ選ぶどんな方策（多数決・ルータ・
cascade・検証つき union）も、**共倒れ率 `β`（全メンバが同じ問いで誤る割合）に対して `1 − β` を超えられない**。
`gama mesh` は β を bench から直接数え、正確な二項区間（Clopper–Pearson 95%）を添えて union−best 利得を
その区間で読み直す。デプロイ*前*に「**certified**（union の 95% 下限が単体最強の 95% 上限を超えた）/ **undetermined**
（利得はあるが 1 ケースの当たり外れと区別できない。創発とは言わない）/ **dead**（入れ子・同一）」を返す。
解析則 `利得 = (1−rho)·(1−p)·(1−(1−p)^(n−1))` の失敗相関 `rho` も出すが最後に回す: 3 体以上では同じ周辺分布・
同じペア相関で β が異なりうる（Chen 2026, arXiv:2606.27288）ので、`rho` は verdict を説明しても保証しない:
```bash
gama mesh --backends gemma,qwen,llama --suite hard
```
両者は上の合成 backend に対する*経済/統計の verdict 層*で、[`soshiki-genron`](https://github.com/akihidem/soshiki-genron)（組織原論）研究repo（`model/market.py` の p>w/s・`model/mesh.py` の脱相関）から移植。「規模でなく構造」を標語から**自分のハードで反証できる**ものに変える。

## 結果
hard 12 問・Mac Studio(MLX) で全部ローカル。測定を公平化済（コード抽出＋トークン予算）──
これは*互角*で、クリーンな勝ちではない:

| | 主権的軽量スタック（7B+24B+32B+tool・振り分け） | 単体 122B |
|---|---|---|
| スコア | **0.92** | **0.92** |
| 取りこぼし | r4（曜日 mod 演算） | c3（roman 数字のコード） |

穴は相補的で同点 ── しかも全部ローカル。再現:
`python3 -m experiments.moa_vs_strong <config.json>`。

### 自分で育つ ── `gama grow`
`bench` は*あなたが書いた*組み合わせを測る。**`grow` は組み合わせの方を書く**。config を 1 手ずつ
変異させ（クラスを別モデルへ振る、レーンを `tool` で包む、統合役を立てて合議にする、検証 gate の
段階委譲にする、未ルーティングの全クラスが乗る既定レーンを差し替える、合成の中にもう一段合成を
入れる、そして**構造を剥がして素に戻す**）、同じ決定的チェッカで全候補を測り、
**held-out split が確認したときだけ**チャンピオンを差し替える。ループのどこにも判定役の LLM は
居ない。

ループ自身の変異も測る価値があり、実際に 1 つ壊れているのが見つかった。提案される ensemble は
`majority` を使っていたが、これは返答を逐語比較するため、自由文では全部が同数になり、
集約結果が黙って**最初のメンバー**になる。graded suite で **0.705 —— 素の 3B の 0.830 を下回り、
レイテンシは 14 倍**。「2 つのモデルに金を払って安い方の答えを採用する」変異になっていた。
現在の提案はもう一方のメンバーに統合させる（同じ case で 0.975・20 問中 8 勝 0 敗）。

```bash
gama grow --models llama3.2:3b,qwen2.5:7b,qwen2.5-coder:7b --generations 4 --width 5 \
          --out grow.jsonl --write-recipe recipes/my-box
```
既定で `wide,hard,brutal`（56 問）をプールし、3 つに割る:

| split | そこで決めてよいこと |
|---|---|
| `search` | 候補を測り、最高点の**1 本だけ**が挑戦者として confirm へ進む（K 個の最大値は上振れするので、これは挑戦権であって昇格の根拠ではない）。競走ではなく**分解能 1 問の足切り**: チャンピオンに 1 問を超えて負けた候補はそのチャンピオンの間は決着済みで、confirm の測定を払わない。同点か 1 問以内の負けなら挑戦権は残る（チャンピオンの search 点は昇格時に一度測ったきりの最大値だから） |
| `confirm` | 昇格を決める唯一の場。**max（confirm 1 問ぶん, チャンピオン自身の測り直しの揺れ）以上**の差を要求する（1 問に満たない差も、自分の揺れより小さい差も、改善ではない） |
| `sealed` | 何も決めない。走り終わるまで一度も触らず、最後に 1 回だけ開ける。だから看板の数字だけは、どの判定にも当てはめていない |

WSL2（CPU のみ ollama）で 12 走まわし（最大 86 問・43/23/20 分割）、構造的な変更が 2 つ見つかった。
`qa` を tool レーンへ通すことと、`research` を外部検証つきで 7B coder へ段階委譲すること。
それぞれが担当するクラスで測ると、`qa` は **0.222 → 1.000**（プールのどのモデルも素では解けない
問題を含む。3 時間 45 分を 15300 秒と答えるが、同じ 3B に「プログラムで」と言うと `3*3600+45*60`
と書く）、`research` は **0.313 → 0.583**。

ここに至るまでに公開済みの結論を 2 回撤回していて、2 回目の方が学びが大きい。
`research → meshflow` は**追加**としては 9 回中 3 回しか昇格せず、だから一度はレシピから外した。
ところがそれを含むチャンピオンを種にした走行で外そうとすると、削除は confirm を 0.142 下げ、
ノイズ幅 0.0217 を大きく超えた。**昇格記録は「その日のチャンピオンに勝てたか」を測っていて、
「入っている状態で何を支えているか」は測っていない。** 2 つの問いは食い違い、レシピが答えるべき
なのは後者。いまは両レーンを載せ、12 走ぶんの記録も一緒に置いてある:
[`recipes/grown-wsl-ollama`](recipes/grown-wsl-ollama)。

別のマシンの 48B（AWS L4 上で llama.cpp が配信する `Kimi-Linear-48B-A3B`・SSH 経由）に向けると、
ループはまず `tool:<クラス>` 変異を 5 本とも却下した（どれも confirm を下げた）。この README は
それを「必要としないモデルへの税」と書いた。同じ 80 問を 20 / **40** / 20 に割り直す（昇格の床が
0.025 に半減する）と、`tool:qa`（+0.031）と `tool:research`（+0.031）が昇格し、封印スコアは
0.833 → 0.850 へ動いた。

どちらの測定も正確で（drift は終始 0.0000）、食い違っているのは計器ではなく集計の方。
**効果は case ごとに向きが違い、大きさは 40 問中 1 問ぶん。それより粗い分割は、引きしだいで
ゼロとも害とも報告する。** 本プロジェクトが撤回した結論はこれで 3 つ目で、3 つとも出どころは
同じ「1 つの分割からの断定」。

作用するクラスに十分な case があれば、ループは落ち着く。ただし 3B とは**別のチャンピオン**に。
`qa` を 32 問（うち半分は意図的に非計算）にし confirm を 48 問にすると、
`qa → ensemble（同じ重みの温度違い 2 本）` が **+3.00 問**、`research → tool` が **+1.37 問**で
昇格し、封印は 0.861 → 0.875。同じ走行で、3B の看板だった `tool:qa` は**ちょうどゼロ問**で却下された。

この対比が「レシピを写すのでなくループを回せ」の全論拠になっている:

| 箱 | チャンピオン |
|---|---|
| WSL2 CPU・`llama3.2:3b` | `qa → tool` / `research → mesh(3b→coder7b)` |
| AWS L4・`Kimi-48B` | `qa → ensemble（温度違い）` / `research → tool`（run R。recipe が今出荷しているのは run W の `qa → tool` / `research → ensemble`） |

**両クラスとも持ち主が入れ替わった。** 詳細は
[`recipes/grown-aws-kimi48b`](recipes/grown-aws-kimi48b)。`tool:qa` が 1.25 問からゼロへ落ちた
理由もそこに書いてある。`qa` クラスが純粋な算術でなくなったから。tool レーンが助けるのは算術で、
ルーティング表が振り分けるのはクラス。**クラスの中身が実際のクラスを表していないベンチは、
間違った粒度の判断に太鼓判を押す。**

ここから引きたくなる教訓にも、算数の側から 1 つ訂正が要る。**「case を増やせばよい」は一般には
成り立たない。** 床は `1/n`、利得は `S/n`（S = 実際に改善した case 相当数）で、**両方が同じだけ
縮むので比は S のまま**。変異が触らないクラスの case を足しても 1 ミリも動かない。要求は
`S >= 1`、つまり「**丸 1 問ぶん動いたか**」であって、効くレバーは**変えているクラスの case を
増やすこと**。ループは利得を分数でなく case 単位で報告するようにした。

モデルプールを丸ごと入れ替えると（`gemma4:e2b` + `qwen2.5:7b`・素から）、5 世代で昇格ゼロだった。
種が最初から search 0.959 で、**その suite はそのモデルに対して飽和している**から。この走行は
「構造が移植できるか」には答えられない代わりに、もっと鋭いことを言う。同じ封印 20 問で、
素の 7.2GB モデルが **0.950（10.85s/問）**、構造化した 3B が **0.865（2.02s/問）**。
構造が買ったのは*安いモデルが使い物になること*であって、天井の高さではない。レイテンシを
払えるなら、構造より規模の方が簡単。それを数字にするために `gama market` がある。

却下がループの仕事の大半で、しかも門のあらゆる部分から出る。挑戦権を得られなかった候補、confirm
の改善は本物だがその世代のチャンピオン自身の揺れより小さかった候補（+0.054 対 敷居 0.071）、
split が粗すぎて証明できなかった候補。台帳にはそれも、**最有力の変更が一度も提案されないまま
終わった走行**（探索幅が狭く別候補がキュー先頭に居座った）も残してある。台帳上、不在は却下と
同じ顔をする。台帳を残す理由がそこ。

#### 封をした split が、走行そのものについて言うこと

上の門はすべて `confirm` の上で判定している。その `confirm` は**毎世代くり返し選択に使われる**
ので、`search` と同じ理由で、一段深いところで上振れする。`sealed` は最後に一度だけ開けて
どの判定にも使わないので、走行全体を裁ける唯一の目になる。昇格が起きた走行で見ると:

| 走行 | confirm の言い分 | sealed の言い分 |
|---|---|---|
| Q | +6.25% | +1.65% |
| R | +8.85% | +1.39% |
| T | +0.45% | **−1.79%** |

4〜6 倍の上振れ。伸びが小さいところでは符号ごと反転する。run T は champion を出力し
`promotions: 1` と報告したが、封を開けた側は「種より悪い」と言っていた。数字は台帳に在って、
誰も見ていなかった。走行の最後に、sealed 自身の分解能(1 問)で帯を切った 3 値の判定を出す:
**改善した / 悪化した / 区別できない**。「分からない」を「効いた」に丸めないことがこの判定の
全部で、これはこの repo が何を主張できるかを変える。完了した 9 走のうち **7 走が NOT
SEPARABLE**。帯を越えたのは WSL の `llama3.2:3b` 走(sealed 20 問で 0.6375 → 0.8542・+4.33 問)と、
48B の run W(sealed 32 問で 0.7484 → 0.8214・+2.34 問)。ただし W の種は前の champion なので、
区別がついたのはその champion からで、素のモデルからではない。鎖の最初の輪は区別がつかないまま。

つまり正直な見出しは「ループが良い組み合わせを育てる」より狭い。小型モデルと飽和していない
suite では実際に育った。48B では、7 走ぶんの昇格を重ねても(その箱で final 行まで書いた台帳の
全部。捨てた走行も数に入れる)、封を開けた問題では出発点と区別のつく champion は出なかった。
8 走目で出た。難しい問題(`crux`)を足し、種が既に育った設計だった走行で。

#### 伸びしろがどこに在るか

この結果には測れる原因があり、それは門ではない。ある走行の confirm 56 問で、クラスごとに
「まだ取れていない点」を数える:

| クラス | 問数 | 得点 | 伸びしろ(取れる余地・問) |
|---|---|---|---|
| integration | 8 | 1.000 | **0.00** |
| code_implementation | 8 | 0.938 | 0.50 |
| qa | 16 | 0.922 | 1.25 |
| content | 8 | 0.658 | 2.73 |
| research | 16 | 0.812 | 3.00 |
| **合計** | **56** | **0.866** | **7.48** |

56 問中 46 問がすでに満点。昇格には 1 問ぶんの価値が要るので、suite 全体でも昇格 7 回ぶんしか
余地が無く、レーン変異 1 手が動かすのは 1〜3 問 ── sealed の分解能の内側になる。これが 6 回の
NOT SEPARABLE の機構で、**効く手は問題を増やすことではなく、難しくすること**だと言っている。

「分離できない」は一語で三つの結果を指していて、ループはいまどれかを言う。sealed が検定する
仮説は**最終形 vs 種**なので、直すべき主張は「最終形が `confirm` で種より何問上に立つか」
(選択に使っていない測定の平均: 種の測定は全部、最終形は昇格後の測り直しで、昇格時の点は
入れない)を sealed の問数に直したもの。run T は +0.84/56 問 → sealed 28 問なら 0.42 問で、
sealed が分解する 1 問の内側。判定は**封を開ける前から決まっていた**。run R は +4.0/48 →
sealed 24 問で 2.0 問見えるはずが +0.33 問。こちらは confirm の伸びが**転移しなかった**＝昇格は
選択の上振れだった。run V は三つ目: 門は昇格時に +1.1 問を認定したが、最終形はその後毎世代
測り直され(昇格時 0.784、以後 0.779/0.764/0.761/0.759、種は 0.767)、confirm で種より
**0.08 問下**で終わった。主張は封を開ける前に**蒸発**していて、昇格時の点が選択、測り直しが
訂正だった。一つ目は sealed を広げる(か大きな手を通す)話、二つ目は昇格を疑う話、三つ目は門が
ノイズを認定したという話。走行は種の時点で sealed の分解能を confirm の問数で印字するので、
検定力の無い走行は終わる 3 時間前に自分でそう名乗る。

この伸びしろには但し書きが要る(モデルではなく checker 側を監査して出てきた)。チャンピオンが
落としている 10 問のうち **4 問は内容だけでなく出力形式も採点している**(正解を散文で包むと
0 点になる checker)。その 4 問が 7.48 問中 3.25 問ぶんを占める。つまりそこでは「解けない」と
「言われた形で答えなかった」が分離できていない。リポグラムのように形式そのものが課題の
ケースもあるので全部が誤りではないが、残っている余地の一部は推論の余地ではないかもしれない。
確かめるには実際の応答が要り、台帳は得点しか持っていないので、これは結果ではなく未解決の問い
(以後の走行は台帳の隣に call ごとの記録も書くので次の走行なら答えられる。上の数字を出した走行に
それは無い)。
`crux` は最初から緩い規約で書いてある ── 数値は「返答の最後の整数」で読むので、解いたうえで
一言添えたモデルもちゃんと取れる。

同時にこれは、ループに経験則でなく証明を与える。足す変異は自クラスの case しか触らないので、
伸びしろが門に満たないクラスは何を当てても昇格しえない ── なのに満点の `integration` に実 GPU
時間を払っていた。そこは飛ばす。ただし削る変異は飛ばさない: 門が非対称(足す側は良くなること・
削る側は悪くならないことしか要求しない)なので、満点のクラスはむしろ「その構造は何も買って
いない」と言える最良の場所になる。

**`--suite edge` は、その `crux` が次に飽和したときに足すもの。** 実際に飽和した: 出荷 champion
(`qa` が既に tool レーン)を種にした走行は、search 側の伸びしろを `code_implementation` 0.5 問・
`qa` 0.25 問と報告し、3 世代目からその 2 クラスを additive 変異から外した。これは `crux` が設計
どおりに効いた結果で(プログラムで解ける帯を狙ったのだから、プログラムを走らせるレーンが取る)、
同時に次の天井でもある。`edge` はもう一段ずらす: **素直に書いたプログラムが間違う** 20 問。
硬貨 `[1, 3, 4]` の貪欲法、0 方向に丸める RPN の除算、後戻りの要る `*`、2 桁の反復数、重複文字の
`next_permutation`。プログラムが助けにならないクラスには「読みが確定して見えて確定していない」
問い(時計の針が 1 日に重なる回数)を置いた。答えはすべて総当たりか独立の計算で確かめてあり、
コード 8 問には「正しい実装ともっともらしい誤りを分ける引数」を最低 1 つずつ入れてある。

**書いた相手で測ったら、狙いの半分は外れていた。** 最初にこの suite を含めた走行の種は
`edge` で 0.679(`crux` 0.385・`wide` 0.850)。伸びしろは確かに増えたが、狙った場所ではない:
その測定に出た `edge` のコード 12 コールは**全部満点**だった。Kimi-48B は `min_coins`・`rpn`・
`lis_length`・`next_permutation`・`decode_rle`・`covered_length` を、分別用の引数ごと正しく書く。
「素直に書いたプログラムが間違う」は、この箱のモデルより弱いモデルに合わせた勘だった。実際に
分かれたのは `content`(2 コール中 0.00)・`integration`(2 中 0.00)・`research`(6 中 0.17)で、
答えが手順や形の側にあるクラス。suite は「どこで落ちるか」の仮説で、この仮説は半分当たった。
次の版は当たった半分に寄せる。

#### tool レーンには前提条件があり、**一番効いてほしい所で外れる**

`crux` はこの箱の飽和を解くために書いた。実際に解けた: 素のモデルは旧 pool で 0.866 だったのが
crux では 0.306、伸びしろは 7.48/56 に対して 11.80/17（1問あたり5倍）。
ところが `research → tool` を積んだ出荷 champion は、crux の research 4問を **1問も直せなかった**。
友愛数・Collatz・完全順列・Josephus ── どれも5行の Python で解ける。

レーンはプログラムを一度も走らせていなかった。これらの prompt でモデルは ```python を
まったく出さず、`ToolBackend` は生の返答をそのまま返す（fall back）。その生の返答は途中で
切れた思考文なので、**素のモデルより悪い点になる**（素のモデルは少なくとも答えを言う）。
例外にはならないので、ただの低得点として届く。

原因の切り分け（推測でなく実測）:

| 疑い | 検証 | 結果 |
|---|---|---|
| 生成コードが実行上限に当たる | 素朴な解法を計測 | 2.9秒・0.7秒（上限15秒の内側） |
| 指示が衝突している（case「整数だけ返せ」× PAL「コードだけ返せ」） | 衝突を明示的に解消 | それでも code block は出ない |
| token 予算が足りない | 1536 / 4096 / 8192 | 1536・4096・**8097** tok を使ってどれも code block なし。8192 では自分から停止 |
| 温度0の縮退ループ | temp 0.0 と 0.8 を3問ずつ | 0/3 対 1/3 ── ノイズの内側で、修正とは言えない |
| モデルがフェンスを**開かない** | 返答の冒頭として ` ```python ` を渡す（assistant ターンを末尾に付ける） | **3問中2〜3問でコードが出る**。正解は 1/3 |

正直な読みはモデル側の話になる。`Kimi-Linear-48B-A3B-Instruct-IQ2_M` は約2bit 量子化で、
複数文の prompt に対して確実にフェンス付きコードを出す、という指示追従はまさに劣化する部分。
**PAL レーンは無料の構造的勝利ではなく、「モデルが本当にプログラムを書く」方への賭け。**
そしてその賭けは**問題が難しくなるほど分が悪くなる** ── 効いてほしい方向と逆。

ループにこれは直せない。ただし**隠してはいけなかった**。tool の呼び出し回数と実際に走った
回数を測定ごとに数えて出すようにしたので、「tool レーンの点が悪い」と「tool レーンが一度も
使われていない」が同じ顔をするのをやめた。

次の一手は当然「ループにレーンを剥がさせる」で、ここでの予想は「剥がすだろう」だった。剥がさ
なかった。しかもループ自身の数字では剥がさないのが正しい: 出荷 champion を種に crux を pool に
入れて回すと、`simplify:qa → 素` は confirm で champion の 0.761 に対し 0.729、`simplify:research →
素` は 0.759 に対し 0.743。crux の research を全問落としながら、それぞれの tool レーンはまだ
差し引き 1〜2 問ぶん稼いでいる。**暴くために作った case で壊れているレーンが、残りの case では
元を取っていることがある。** recipe は両方を積んだままで、走行は
[`recipes/grown-aws-kimi48b`](recipes/grown-aws-kimi48b) の注記に残した。

この箱の全台帳を数えると、それがそのまま傾向になっている: 削減の枝は confirm 測定を 14 回
焚き、13 回は「明確に悪い」で終わり、14 回目の昇格はサーバが死んで champion も削減も 0.0000
だった走行のもの。しかも 13 回とも、その前に **search** で帯を超えて負けていた。だから削減も
追加と同じ**費用の門**を通る: 帯の外なら confirm は焚かない。判定の門は非対称のまま(足す側は
良くなること・削る側は悪くならないこと)で、同じにしたのは「測る価値があるか」の判断だけ。
過去に当てると判定は 1 つも変わらず、唯一の偽の昇格は測る前に落ちる。search で落ちた削減は
challenged でなく settled に入るので、チャンピオンが替われば同じ手をもう一度問える。

表の最後の行だけがモデルを動かした。しかもそれは prompt でなく**レーン**の変更で、
`ToolBackend(prefill="```python\n")` がモデルに自分の返答の書き出しを渡す。残る判断は
フェンスの中に何を書くかだけになる。レーンごとの opt-in にしたのは、このモデルがもともと
コードを書けている suite でどう転ぶかは未測定で、測るのはループの仕事だから。だから変異にした:
あるクラスが `tool` レーンに乗ったら、ループが次に出す 1 手の洗練は `tool:<class>(model)+prefill`
で、他と同じ門を通る。3 問中 2 問がコードに到達し、正解は 1 問。それが confirm の 1 問を買うかは
台帳が言う。（返答はサーバが末尾の assistant ターンをどう扱うかで 3 通りの形で戻る ── 続きを書く・
フェンスを開き直す・開いて閉じない。抽出は 3 つとも読む。違いはサーバ側のもので、モデルの仕事では
ないから。）

候補の列はその診断を読む。測定はクラスごとに「tool の call がコードブロック無しで返った回数」
（`tool_no_code_by_class`）を残し、症状のいちばん多いクラスの `+prefill` が tool 枠の先頭に出る。
これが無いと順番は巡回のもの: run W の種は confirm で「コード無し 8/72」、全部 research と
言っていたのに、gen1 の tool 枠は `tool:qa(kimi-cold)+prefill`（qa の tool レーンはもともと
コードを返している）に行った。その checkpoint から `propose()` を再生すると（モデルは焚かない）、
research の prefill は gen2、巡回 1 つ後ろに並ぶ。この段落は最初、巡回の規則だけから「5 世代の
うちには来ない」と書いていて、再生がそれを訂正した。run W で診断が買ったのは 1 世代ぶん。
変わるのは順番の出どころで、巡回がたまたま始まった位置ではなく、測定になる。

ただし、並ぶことと `confirm` で測られることは別。`search` で同点の候補から挑戦者を選ぶのは構造の
大きさ、次にラベル順で、prefill はチャンピオンと同じ大きさ、`route:` と `ensemble:` は `tool:`
より前に並ぶ。run W の種から診断（全部 research）を付けて再生すると、research の prefill は gen0
に並び、以後の世代も毎回並ぶが、挑戦者は `route:content`、`ensemble:research`、`default`、
`route:research`、`route:qa`: 5 世代、処方には一度も来ない。だから診断は*処方*を名指しし、処方は
種類の巡回を待たずにその世代の最初の席を取り、同点なら confirm の測定も先に取る。費用は測定 1 回
きり: 測れば archive に残ってコール 0 で並び続け、却下されれば除外される。confirm の 1 問を買うか
は台帳が言う。そして台帳は人の手を借りずにそれを言う: 世代行は診断と候補に並んだ処方を記録し、
挑戦者の行は処方だったかを持ち、結果は処方ごとに「並んだ世代数・confirm を測られた回数・昇格した
回数」を数える。recipe はその数を印字する。run W の「処方は一度も測られなかった」は台帳を再生して
見つけ、recipe に手で書いた。いまは走行が自分で言う。

#### 症状は 2 種類になった(切断と、その処方)

trace は台帳が答えられない問いに答える。trace を持つ最初の走行は、種の測定でいきなりそれを
出した: 26 コールが max_tokens で切られていた(qa 16・integration 8・content 2)。最初の 76
コールのうち integration の切断 4 本は**全部 0.0**、qa の切断 4 本は**全部 1.0**。同じ症状で
意味が逆になる: qa は tool レーンで、枠が尽きる前にコードブロックが閉じている。integration は
返答の末尾の数値が答えなので、届かなかった返答は 0 点になる。

だから切断はクラス単位の症状で、治療もクラス単位。`Measurement.cut_by_class` は「切られ、かつ
満点に届かなかった」記録だけを数える(切れても満点なら症状ではない。処方の席を使わせない)。
`propose` は症状のあるクラスにだけ 1 本鋳造する: そのクラスのレーンの中の `max_tokens` を
深さに関わらず全部 2 倍(上限 8192。上限があるので毎世代 2 倍が続かない)。症状のある所にしか
出さないのは、枠を増やす費用(待ち時間とコール)は必ず掛かる一方、切れていないクラスでは効き
ようがないから。席は処方枠で取り、判定は他の変異と同じ門でする。

診断と治療は**対で**突き合わせる(クラスだけで合わせない)。切断しか出ていない世代に、その
クラスの `+prefill` が処方として最初の席を取ってしまうと、測定が言っていない症状の治療に
その世代を使うことになる。

#### 3 つ目の症状: 答えは在って、前置きに包まれていた

同じ trace の同じ種の測定で、`content` の 56 コール中 12 本が `Sure! Here's a sentence that
meets your criteria:` と前置きしてから答えを**太字で**返していた ── prompt は「その文だけを
出力せよ」と書いてある。他のクラスは 0 本(code 80・qa 120・research 120・integration 68 で
いずれも 0)。`content` はこの pool で最も点の低いクラスでもある(0.387)。モデルは文を書け
ないのではなく、文だけを渡せていない。

これが 3 つ目の症状で、治療は枠でも道具でもない: レーンに system の一行を載せる ──
「Reply with only what was asked for: no preamble, no sign-off, no commentary about the answer」。
`SshOpenAIBackend` が `system=` を受け取り、`Measurement` は `preamble_by_class`(返答の
先頭が挨拶で、かつ満点に届かなかった記録)を数え、`propose` は症状のあるクラスに
`terse:<class>(<lane>)` を鋳造する ── 同じレーンの、system を受け取れて**まだ空いている**
backend 全部にその一行を入れた写し。既に載っているものは上書きしない(それは 2 手になる)。

診断はわざと狭くしてある。見落としは「席が出ない」だけだが、誤検出は効きようのないクラスに
測定 1 回を使わせる。だから語彙は挨拶(`sure`・`certainly`・`here's`・`below is`)に限り、
推論の書き出し(`let me compute ...`)や、答えそのものでありうる語(`yes`)は入れない。

#### いちばん取り分の大きいクラスが、診断からいちばん遠かった

走行中の種の測定を、クラス別に「まだ取れていない confirm の問数」で読むと: `research` 4.62、
`content` 4.58、`integration` 3.00、`qa` 1.25、`code_implementation` 0.50。走行はこの行を、
3 つの診断が各クラスに何を見ているかと並べて出すようになった。

`research` はいちばん大きな損で、しかも**症状が 1 つも見えていない**クラスだった。返答を読むと
理由が書いてある。種の測定で「1000 字を超えて、文の途中で終わり、満点に届かなかった」返答が
15 本。`Thus the unique consistent assignment is: A = L, B = T, C =` で切れている導出まである。
そのうち 8 本は `finish_reason: length` と記録されていて、8 本とも `integration` か `qa`。
残り 7 本は全部 `research` で、記録は `None`。違いはモデルでも prompt でもない ── `research` は
出荷 champion が**合議に振っている唯一のクラス**で、合議は停止理由を名乗らないから、切断の診断は
いちばん届いてほしいクラスに構造的に届いていなかった。木を歩く修正が塞いだのはこの穴で、
隠れていた大きさは `research` の 4.62 問のうち confirm の 3 問ぶん。

#### ループ自身が間違っていて、自分では見えなかったこと

**決定的でなかった。** `search` で同点の候補から挑戦者を選ぶとき、実測レイテンシで割っていた。
壁時計は共有の箱では他人の負荷でも動くので、同じ入力の 2 走が別の経路を通りうる。determinism
テストは前から在って、誰が走らせても通っていた ── 80 回中 4 回落ちる。同点は構造の大きさで
割るようにした。spec だけで決まり、追加コールを生んでいる当のものでもある。

**相手が同じだと仮定していた。** ある走行は、途中で持ち主が別モデルに載せ替えたサーバを相手に
判定していた。捕まえられたのは載せ替えが 503 を返して error_rate の床に当たったからで、200 を
返し続ける載せ替えなら、世代 0 と世代 5 を別モデルで比べたまま一続きの改善として報告していた。
応答は毎回どのモデルが答えたかを名乗るので、宛先ごとに同じ実体へ解決され続けているかを追加
コールゼロで検査し、測った相手を recipe に書き出すようにした ── 量子化違いは別のモデルなので、
「Kimi-48B」だけでは数字を再現できない。

**古い最大値を相手に `search` で競走させていた。** 門 ① は挑戦者に「search でチャンピオンを
厳密に上回れ」と要求していた。だがチャンピオンの search 点は昇格時にその世代の幅の最大値として
一度測ったきりで、二度と測り直されない。confirm の方は毎世代測り直される（ある走行で 0.784 →
0.779 → 0.764 → 0.761 → 0.759）。同じ spec を 32 問の search で測り直すと丸 1 問動いた（0.896 と
0.865）。その分解能で 0.5 問の負けを負けと読み、confirm は挑戦者 1 本にしか測らないので、confirm
で **4 勝 1 敗**・**4 勝 0 敗**（p = 0.0625）と測れていた候補を、測らないまま捨てていた。いまの
`search` が決着させるのは 1 問を超えて負けた候補だけで、同点と 1 問未満の負けは挑戦権を残し、
決めるのは confirm の門。副産物は節約で、search で決着した候補にはそれ以上何も払わない
（以前は世代ごとの挑戦者が判定に関わらず confirm 1 回ぶんを払っていた）。

**深くしたレーンが袋小路だった。** ループは `mesh` や `ensemble` レーンの内側に `tool` 段を
入れ子にできる（`mesh(a->b)+tool`）。合成レーンの素モデルを引く関数が同じファイルに 2 つあり
（spec を読む版と名前を解析する版）、定義順で名前解析版が勝っていた。それは `tool(a)` と
`mesh(a->b)` は読めるが `mesh(a->b)+tool` は読めない。だから一度深くしたクラスは、素に戻す・
別の包み方をする・組み直す、のどれもできず、振り替えるしかなかった。変異が取れる方向は、
ループが作りうるどの形からも届いていなければならない。さもないとループは一方向に流れて、
それを結果と呼ぶ。いまは spec を先に読み、名前を解析するのはループ自身が鋳造する名前空間の
内側だけ。

**測定済みの設計が席を取っていた。** `width` はループが 1 世代に測る設計の数。archive に
ある設計はもう一度並べてもコールは要らないし、並べ直さなければならない: 帯の内側にいて最高点で
なかった候補は、最高点が `confirm` で落ちた次に archive の点のまま挑戦できる踏み石だから。
なのに 1 本ごとに width の席を使っていた。全部同点の走行（run W の search 分割は未解決が 4 問で、
たいていの変異はそこを動かせない）で W の gen0 checkpoint から再生すると、6 世代の新顔は
4, 3, 2, 3, 1, 0 で、gen2 に並んだ research の prefill は二度と出てこない: 踏み石が戻るのは巡回が
たまたまその設計をもう一度出した時だけだった。いまは archive が挑戦者の母集団で、測定済みで決着の
ついていない設計は毎世代 width の外に全部並ぶ（同じ再生で 4, 4, 4, 3, 0, 0。末尾の 0 は 1 手で行ける
15 本を測り切ったから）。台帳は `candidates`（並んだ数）と `new_candidates`（測った数）を分け、
挑戦者が新顔か archive から来たかを残す。

**recipe が違うコードの名を書いていた。** 台帳は git の commit を刻印する。判定が変わった
2 走を、同じ走行条件のまま見分けるためのもの。それを書く時点で `HEAD` を読んでいた。run W の
seed 行は `e7e5e63`、recipe は `ffdb5bf`。後者は走行が測定中に積まれた commit で、数字には
何も寄与していない。run X はもっと悪く、`HEAD` に未コミットの編集を載せた tree を import して、
刻印は `HEAD` と言った。刻印は走行につき 1 回になり、その時点で package dir が commit と
違っていたかを `dirty` として並べて残す。`dirty` は「commit ではない」と言うだけで、run X の
刻印は結局「起動時に disk にどの編集まであったか」を記憶から辿って直すしかなかった。だから
刻印は package dir 配下の `*.py` 全部の指紋 `source`(`source_hash()`。走行が import する
source そのもので、使われない module も含む)も持つ: 同じ指紋は実用上同じ source(SHA-256 の
64 bit)で、任意の commit の指紋を後から計れば、どの commit が(あるいはどれでもないことが)数字を
出したか言える。

**門は揺れを違う側から借りていた。** 昇格は `max(confirm 1 問ぶん, チャンピオン自身の測り直しの
揺れ)` を超えなければならない。その揺れはチャンピオンのもので、48B の pool のチャンピオンは
temperature 0: 揺れは毎世代 0.0 で、敷居はいつも 1 問の床だった。挑戦者の揺れはどこにも入って
いない。run V は `route:content->kimi-hot` を +1.1 問(2 勝 0 敗)で昇格させ、run W は同じ設計を
同じ 65 問の confirm で −0.9 問(1 勝 3 敗)と測った。2.0 問の往復を台帳の何も予告できなかったが、
どの測定も既に払っている repeats がその見積もりを持っている: 各測定は repeats から平均の標準誤差を
記録し、比較(挑戦者の伸び・削減の下落・sealed の判定)はそれぞれ差の測り直しの揺れを問数で伸びの
横に書く。記録であって門ではない: 過去の台帳にこの数字は無く、過去の昇格を何本止めたかが分から
ない。爆風の測れていない門は、数字を運んだ後に入れる。

**台帳は「なぜ」を言えなかった。** 台帳が持つのは点と門の理由で、返答そのものは持たない。run X は
処方の `tool:research(kimi-cold)+prefill` を測って search で 1.25 問負けたが、どの返答で負けたか、
処方の元になった code 無しの tool 返答が「モデルがコードを書かなかった」のか「`max_tokens` で
切れた」のかを台帳は言えない(2048 トークンでの探りでは research の返答が 8〜9K 字で code 無し。
切断を指しているが、走行そのものではない)。走行はいま台帳の隣にもう 1 ファイル
(`run.jsonl` の隣に `run.trace.jsonl`。`--trace` で置き場を変えられる)を書く。call ごとに 1 行:
世代(seed の測定と最後の sealed は世代の外なので無し)・役(champion / candidate / challenger /
simplifier / seed)・split・case・点・トークン・返答の長さ・
先頭と末尾 200 字・サーバの止まった理由(`stop` / `length`)・tool レーンを通った call はその状態。
全文は持たない(切れた返答は 1 問 8〜9K 字。`crux` が答えを読むのは末尾)。台帳はそのままなので
`--resume` と台帳を読む道具は触らず、trace は台帳に従う: 自分の台帳へ続ける走行では追記(先に
`resumed` の行を置くので、checkpoint に届く前に落ちた世代の call と測り直しを読み分けられる)、
台帳が空から始まる時は trace も空から。走行は最後に自分の書いたファイルを数え直して、result・
recipe・stderr の 3 か所に「トークン上限で切れた call が何件・どのクラスか」を言う
(`per-call trace: <calls> calls; cut at the token limit (finish=length): <n> (<class>: <n>, ...)`)。
止まった理由を言わない backend では「分からない」であって 0 ではない。読み返すのは
`gama trace run.trace.jsonl`: 設計 × 役 × split の表(call 数・平均・切れた数。隣の台帳から label を
引く)、`--rows --finish length --class research` で切れた返答を末尾つきで 1 行ずつ、
`--diff <種の hash> <候補の hash>` で 2 設計の case ごとの差(それぞれの全測定の平均。champion は
5 回測られるので「最後の 1 回」で比べない)。台帳の件数では答えられなかった「どの case で動いたか」
がこれ。

## レシピ ── みなで育てる 🌱
`recipes/` はコミュニティ・ライブラリ。1 レシピ = `config.json`（組み合わせ）＋ `recipe.md`
（モデル群・ハード・`gama bench` の数値）。あなたの箱で大きいモデルに並ぶ小型の組み合わせを
見つけたら、**レシピを追加** ── [CONTRIBUTING](CONTRIBUTING.md) 参照。
```bash
gama recipes                       # 一覧
gama recipes mac-studio-mlx        # レシピの config を表示
gama run "47*53+89*17 を計算" --config recipes/mac-studio-mlx/config.json --task-type qa
```

## 正直な注意
- 同一モデルのコピーを重ねても **無意味** ── 効くのは多様性（別々の blind spot）。`gama mesh` は
  これを共倒れ率 `β` で数える: 同一/冗長メンバは同じケースで落ちる → union = 単体最強 → verdict `dead`。
- 全メンバーが共有する穴は小型アンサンブルでは塞げない ── 共有する hard core がそのまま β で、
  そのメンバから答えを選ぶどんな方策も `1 − β` を超えない。そこは道具か、大きいモデルが要る
  （ペアの `rho` は 3 体以上でこの尾を見られない。だから `gama mesh` は β を最初に出す）。
- 異種アーキの比較は公平な答え抽出＋十分なトークンが要る。さもないとモデルでなくハーネスを
  測ってしまう。
- `tool` とコードのベンチケースは **モデル生成 Python を実行** する ── 信頼できる backend で
  のみ（opt-in・サンドボックス的）。
- 選抜に使った split で測った伸びは、伸びの推定値ではない。`grow` の数字を引くなら **sealed**
  の方を引き、判定も一緒に引くこと。
- `grow` は挑戦ごとに case 別の勝敗を記録して符号検定の p 値を出すが、**既定では門にしない**。
  この問数だと有意には全勝級(5勝0敗・8勝1敗)が要り、有効にするとループが止まる。要るなら
  `--max-paired-p`。数字自体は読む価値がある ── 56 問中たいてい 1勝2敗で、この suite が
  構造を区別できない理由がそこに全部出ている。
